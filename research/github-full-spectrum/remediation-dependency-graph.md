## Remediation definitions

### R1 — Security verification

Observe effective state of public-repository minimum controls. Never infer disabled state from connector absence.

### R2 — Target main ruleset

Minimum target: PR required, `validate` required, conversation resolution, block force push, block deletion. No fake required reviewer in a single-owner repository.

### R3 — Required check identity

Confirm the stable check context/source generated by `.github/workflows/validate.yml` before configuring the ruleset.

### R4 — Governance application

Requires an admin-capable UI/API path not currently exposed by this connector. Apply only after exact configuration is documented.

### R5 — Validator/reference tests

Promote only justified invariants. Avoid introducing a runtime/toolchain just for lint theater.

### R6 — Documentation/repository identity

`SECURITY.md`, CITATION, description/topics and removal of unused surfaces are independent small changes. LICENSE remains a separate legal decision.

### R8 — Lifecycle tests

Governance must already be effective so failure-path tests prove enforcement rather than merely workflow behavior.

### R11/R12 — Tag and Release

The current connector can read but cannot create these objects. Use GitHub UI/CLI/API under user control after release readiness passes.

## Rollback principle

Configuration changes must have a documented way back to the pre-remediation snapshot. Content changes use Git/PR/revert; settings changes record before/after values; destructive repository operations are explicitly outside automated remediation.
